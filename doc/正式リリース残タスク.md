# KumustaHub 正式リリース残タスク

作成日: 2026-05-09

## 前提

現在のMVPは、Next.js App Router 上で主要画面、検索UI、店舗詳細、管理画面の土台、Prisma schema、Supabase client 雛形、Vercel デプロイまで完了している。

正式リリースでは、ローカルシードデータ中心のMVPを、実データ・認証・投稿・管理運用・法務・監視まで含む公開サービスへ引き上げる。

## リリース判定基準

- ユーザーが店舗を検索し、詳細を閲覧できる
- Google/Facebook OAuth でログインできる
- ログインユーザーが口コミ、写真、お気に入り、通報、店舗追加申請を使える
- 管理者が店舗、口コミ、通報、店舗追加申請を運用できる
- 初期重点エリアの店舗データが十分に登録されている
- 利用規約、プライバシーポリシー、問い合わせ、削除依頼導線が公開可能な内容になっている
- SEO、OGP、sitemap、robots、基本計測、エラー監視が設定されている
- 本番環境のセキュリティ設定、RLS、バックアップ、権限管理が確認済み

## 実施順

### 1. 本番基盤の確定

優先度: P0

目的: 以降の開発が実DB・実認証・実Storageを前提に進められる状態にする。

タスク:

- Supabase 本番プロジェクトを作成する
- PostgreSQL 接続文字列を取得する
- Vercel/serverless 用に Supabase Transaction pooler の接続文字列を取得する
- migration/admin 用に Supabase Direct connection の接続文字列を取得する
- Supabase Auth の Site URL と Redirect URLs を設定する
- Google OAuth provider を設定する
- Facebook OAuth provider を設定する
- Supabase Storage に review photos 用 bucket を作成する
- Vercel に本番環境変数を設定する
  - `NEXT_PUBLIC_SUPABASE_URL`
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  - `DATABASE_URL`: Transaction pooler
  - `DIRECT_URL`: Direct connection
- 独自ドメインを使う場合は Vercel にドメインを設定する
- Vercel と GitHub を接続し、main branch の自動デプロイを有効化する

完了条件:

- Vercel production build が Supabase 環境変数つきで成功する
- OAuth ログイン開始から callback まで到達できる
- Storage bucket へテスト画像をアップロードできる

### 2. DB migration と RLS

優先度: P0

目的: Prisma schema を実DBへ反映し、ユーザー権限境界を本番水準にする。

タスク:

- Prisma migration を作成する
- Supabase PostgreSQL に migration を適用する
- `stores.search_text` の生成方針を決める
- PostgreSQL Full Text Search 用 index を追加する
- Supabase Auth の `auth.users` とアプリ側 user id の扱いを決める
- RLS policy を設計・適用する
  - 公開店舗は guest が閲覧可能
  - 非公開店舗は admin のみ閲覧可能
  - review 投稿はログインユーザーのみ
  - favorite 操作は本人のみ
  - report 作成はログインユーザーのみ
  - admin 操作は admin のみ
- admin 判定用の role 管理方式を実装する
- DB seed または管理画面経由の初期投入手順を決める

完了条件:

- guest/user/admin の主要操作をRLS込みで検証済み
- Prisma 経由の読み書きが本番DBで成功する
- 不正な user id で他人の favorite や review を変更できない

### 3. データ取得層の実DB化

優先度: P0

目的: `lib/data.ts` のローカルシード依存を外し、本番DBから表示する。

タスク:

- Prisma client の server-side 利用を実装する
- 店舗一覧取得APIまたはserver functionを実装する
- 店舗詳細取得をDB化する
- ブランド、カテゴリ、エリア取得をDB化する
- 検索条件をDB queryへ反映する
  - keyword
  - area
  - category
  - rating
  - tagalog support
- 平均評価と口コミ数の更新方式を決める
  - review 作成時に集計更新
  - または view/materialized view
- ローカルシードデータを開発用 seed として分離する

完了条件:

- 本番DBの店舗データが `/search` と `/stores/[slug]` に表示される
- DB上で非公開の店舗が公開画面に出ない
- 検索条件が期待通りに絞り込む

### 4. 認証とログイン必須操作

優先度: P0

目的: 閲覧は guest、投稿系は user という制御を実装する。

タスク:

- Supabase SSR auth helper を App Router に組み込む
- middleware でログイン必須ページを保護する
- `/login` の Google OAuth ボタンを実動作にする
- `/login` の Facebook OAuth ボタンを実動作にする
- ログアウト導線を追加する
- `/mypage` でログインユーザー情報を表示する
- 未ログイン時の投稿、保存、通報、店舗申請の遷移を整理する

完了条件:

- guest は閲覧可能だが投稿操作時にログインへ誘導される
- user は口コミ、お気に入り、通報、申請を実行できる
- admin 以外は `/admin` にアクセスできない

### 5. 口コミ・写真投稿

優先度: P0

目的: サービス価値の中心である口コミ蓄積を可能にする。

タスク:

- 口コミ投稿フォームを実装する
- 星評価の入力UIを実装する
- 本文任意の validation を実装する
- 写真最大3枚の upload UI を実装する
- Supabase Storage へ写真を保存する
- review と review_photos をDBへ保存する
- 投稿後に店舗平均評価と review_count を更新する
- Helpful を1ユーザー1回に制限するためのDB設計を追加する
- Helpful 操作を実装する
- 管理者による口コミ非表示/削除を実装する

完了条件:

- ログインユーザーが写真つき口コミを投稿できる
- 写真4枚以上は投稿できない
- 投稿後に店舗詳細へ即時反映される
- admin が問題口コミを非表示または削除できる

### 6. お気に入り・通報・店舗追加申請

優先度: P1

目的: コミュニティ機能と運営改善フローを成立させる。

タスク:

- お気に入り保存/解除を実装する
- `/mypage/favorites` をDB化する
- 通報フォームを実装する
- 通報理由の選択肢を定義する
- reports の対応ステータスを管理できるようにする
- 店舗追加申請テーブルを追加する
- `/store-request` をDB保存に対応する
- admin が申請を承認/却下できるようにする
- 承認時に stores へ反映する処理を実装する

完了条件:

- user が保存した店舗だけが favorites に表示される
- user が口コミを通報できる
- admin が通報ステータスを変更できる
- admin が店舗追加申請を承認し、公開店舗へ変換できる

### 7. 管理画面の実運用化

優先度: P1

目的: 運営がコード変更なしで店舗DBと口コミを管理できる状態にする。

タスク:

- 店舗CRUDを実装する
- 店舗の公開/非公開切り替えを実装する
- ブランドCRUDを実装する
- カテゴリCRUDを実装する
- エリアCRUDを実装する
- 口コミ一覧、非表示、削除を実装する
- 通報一覧と対応状態変更を実装する
- ユーザー一覧とBANを実装する
- admin 操作の audit log を検討する

完了条件:

- 運営が初期店舗登録から公開まで管理画面で完結できる
- 問題ユーザーをBANできる
- 非公開店舗や非表示口コミが公開画面に出ない

### 8. 初期データ投入

優先度: P1

目的: 空の口コミサイトではなく、検索価値のある状態で公開する。

タスク:

- 初期重点エリアごとの最低登録件数を決める
  - Ikebukuro
  - Kawasaki
  - Shinjuku / Okubo
  - Yokohama
  - Osaka Namba
- 店舗情報の収集ルールを決める
- 店舗写真の利用権利を確認する
- 営業時間、電話番号、住所、URL、Facebook を確認する
- カテゴリとフィリピン特化項目を付与する
- 初期口コミを運営が作成しない方針を明文化する
- 公開前に店舗情報の重複チェックを行う

完了条件:

- 各重点エリアに最低5件以上、合計25件以上の公開店舗がある
- 住所と地図座標が一致している
- 著作権上問題のない写真だけを使用している

### 9. 地図UIの本実装

優先度: P1

目的: MVPの地図風パネルを、Leaflet + OpenStreetMap の実地図へ置き換える。

タスク:

- Leaflet と React wrapper の採用可否を決める
- dynamic import で client-side map を実装する
- 検索結果に marker を表示する
- marker click で店舗カードへ連動する
- 店舗詳細に地図を表示する
- モバイルでは地図/一覧の切り替えUIを用意する
- OSM tile の利用ポリシーを確認する

完了条件:

- 検索結果の店舗が地図上に表示される
- モバイルでも一覧閲覧を阻害しない
- 外部地図リンクなしで場所を把握できる

### 10. SEO・OGP・多言語

優先度: P1

目的: 検索流入の受け皿としてページ品質を上げる。

タスク:

- title/meta をDBデータから生成する
- 店舗、エリア、カテゴリ、ブランドページの説明文を改善する
- OGP画像を設定する
- sitemap の base URL を本番ドメインへ変更する
- robots の sitemap URL を本番ドメインへ変更する
- canonical URL を設定する
- JSON-LD を検討する
  - LocalBusiness
  - Restaurant
  - AggregateRating
- 日本語/英語UI切り替えの方式を決める
- UI文言を i18n 化する
- 口コミ本文は翻訳しない方針をUI上で自然に扱う

完了条件:

- 主要ページの title/meta/OGP が本番値になっている
- sitemap が本番URLで生成される
- 日本語/英語UIの最低限の切り替えができる

### 11. 法務・モデレーション・安全対策

優先度: P0

目的: 公開サービスとして最低限のリスク対策を入れる。

タスク:

- 利用規約を正式文面に更新する
- プライバシーポリシーを正式文面に更新する
- 問い合わせフォームの送信先を実装する
- 削除依頼窓口を明記する
- reCAPTCHA または Turnstile を導入する
- 投稿・通報・店舗申請に rate limit を入れる
- NGワードまたは簡易モデレーションを検討する
- BANユーザーの投稿制限を実装する
- 管理者削除時の表示方針を決める

完了条件:

- 法務ページが仮文面ではない
- bot投稿を一定程度抑止できる
- 通報から管理者対応までの運用が成立する

### 12. 品質保証

優先度: P0

目的: 公開前の主要導線の破綻を防ぐ。

タスク:

- TypeScript check をCIで実行する
- ESLint をCIで実行する
- production build をCIで実行する
- 主要導線のE2Eテストを追加する
  - 検索
  - 店舗詳細閲覧
  - ログイン必須導線
  - 口コミ投稿
  - お気に入り
  - 店舗追加申請
  - admin の公開/非公開
- モバイル表示を確認する
- Core Web Vitals を確認する
- 画像サイズとLCPを確認する
- 404、空検索結果、未ログイン状態などの例外表示を確認する

完了条件:

- main branch へのPRで lint/typecheck/build が通る
- 主要E2Eが安定して通る
- iPhone相当の幅で主要画面が崩れない

### 13. 本番監視・運用

優先度: P1

目的: リリース後に障害や不正投稿へ対応できるようにする。

タスク:

- Vercel Analytics または代替計測を設定する
- Google Search Console を設定する
- Google Analytics などのアクセス解析を設定する
- エラー監視を導入する
- Supabase の利用量監視を確認する
- DB backup 方針を確認する
- 管理者アカウントの追加/削除手順を作る
- 問い合わせ対応フローを作る
- 店舗情報の修正依頼フローを作る

完了条件:

- 障害発生時にエラー内容を確認できる
- 検索流入と主要ページの閲覧数を追える
- 運営作業の担当者と手順が決まっている

## 推奨マイルストーン

### Milestone 1: 本番DB接続版

対象:

- 本番基盤の確定
- DB migration と RLS
- データ取得層の実DB化

ゴール:

- Vercel 上で Supabase PostgreSQL の店舗データを表示できる

### Milestone 2: ユーザー投稿版

対象:

- 認証とログイン必須操作
- 口コミ・写真投稿
- お気に入り・通報・店舗追加申請

ゴール:

- ユーザーがログインし、口コミ投稿と保存ができる

### Milestone 3: 運営管理版

対象:

- 管理画面の実運用化
- 初期データ投入
- 法務・モデレーション・安全対策

ゴール:

- 運営が店舗DBと投稿を管理でき、公開に耐える初期データが揃う

### Milestone 4: 公開最適化版

対象:

- 地図UIの本実装
- SEO・OGP・多言語
- 品質保証
- 本番監視・運用

ゴール:

- 正式リリース可能な検索流入、品質、監視体制が整う
