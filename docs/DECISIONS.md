# KumustaHub DECISIONS

設計判断記録。重要な技術判断はこのファイルへ残す。

## 2026-05-10: 認証基盤は Supabase Auth を採用

決定事項:

- 独自認証ではなく Supabase Auth を使う。
- Google OAuth は KumustaHub が直接処理せず、Supabase Auth 経由で扱う。
- 管理者判定は `ADMIN_EMAILS` のallowlistで行う。

理由:

- MVP開発速度を優先する。
- Supabase PostgreSQL / RLS / Storage と統合しやすい。
- OAuth callback とセッション管理の実装負荷を下げる。

影響:

- Supabase Auth への依存が増える。
- Google/Facebook provider 設定は Supabase Dashboard と各OAuth provider側の両方で必要。

制約:

- 管理者ロールはDBロールではなく環境変数ベース。
- 将来的に複数管理者や権限差分が増える場合はDB role管理へ移行を検討する。

## 2026-05-10: DBアクセスは server-side Prisma を主経路にする

決定事項:

- 画面表示と投稿処理は Next.js server component / server action から Prisma でDBアクセスする。
- Vercel本番では Supabase Transaction pooler の `DATABASE_URL` を使う。
- migration/admin用途には `DIRECT_URL` を保持する。

理由:

- Next.js App Router と相性がよく、型安全に実装できる。
- Vercel serverless 環境でDB接続数を抑えやすい。
- Supabase client 直叩きよりアプリ側の権限制御をまとめやすい。

影響:

- Prisma経由のDBアクセスはRLSの主な保護対象ではない。
- RLSは将来のdirect Supabase client accessとStorage保護の意味が強い。

制約:

- server action 側の認証/認可チェックを必ず実装する。
- DB負荷が増えたらindex、pagination、cache方針を見直す。

## 2026-05-10: 店舗画像と口コミ画像は Supabase Storage に保存

決定事項:

- 店舗画像は `store-photos` bucket に保存し、メタデータは `store_photos` に保存する。
- 口コミ画像は `review-photos` bucket に保存し、メタデータは `review_photos` に保存する。
- 画像本体はDBに保存しない。

理由:

- DB容量を画像で圧迫しない。
- public URL を使って Next.js Image から表示しやすい。
- 店舗写真のprimary管理や口コミ写真の複数枚管理をDBで扱える。

影響:

- Storage容量とegressが運用上の主要ボトルネックになる。
- 画像の権利確認、圧縮、リサイズが正式リリース前の重要課題になる。

制約:

- 現状は最大5MB制限のみで、リサイズ/圧縮は未実装。
- 外部URL直書き画像は順次Storage管理へ移行する。

## 2026-05-23: 画像アップロードはクライアント側で1200px程度へ縮小する

決定事項:

- 店舗写真と口コミ写真は、アップロード前にブラウザ側で長辺1200px程度へ縮小する方針にする。
- 変換後の保存形式はWebPを第一候補とし、ブラウザ対応や画質問題がある場合はJPEGへフォールバックする。
- 元画像はStorageへ保存せず、表示用に縮小した画像のみを `store-photos` / `review-photos` bucket に保存する。
- 1枚あたりのアップロード上限5MBは残しつつ、変換後の目標サイズは店舗写真500KB前後、口コミ写真300KB前後とする。
- サムネイル生成は別タスクとして扱い、まずは表示用画像1種類への縮小を優先する。

理由:

- Supabase Storage容量とegressの急増を抑えるため。
- スマートフォン写真を5MBのまま配信すると、店舗一覧と店舗詳細のLCPが悪化しやすい。
- MVPではサーバー側画像処理基盤を増やすより、ブラウザ側変換の方が実装と運用が軽い。

影響:

- 投稿前に画像処理が走るため、古い端末ではアップロード開始まで少し待つ可能性がある。
- 画像のEXIFや元解像度は保持しない前提になる。

制約:

- 悪意ある直接POSTやブラウザ非対応ケースに備えて、server action側の形式・サイズ検証は維持する。
- 厳密な画質管理、サムネイル複数サイズ、AVIF変換は後続の画像最適化タスクで扱う。

## 2026-05-23: 本番公開画像はSupabase Storage管理へ寄せる

決定事項:

- 本番公開店舗で使う主画像と店舗写真は、権利確認済み画像を `store-photos` bucket にアップロードし、`store_photos` のメタデータで管理する。
- OGP画像は当面、店舗のprimary photoを使うため、primary photoもStorage管理済み画像を原則とする。
- Unsplashなど外部URL直書き画像は、ローカルseed、fallback data、正式画像が未登録の暫定表示に限定する。
- 外部URL画像の完全撤廃は、初期データ投入時の「外部URL直書き画像をSupabase Storage管理へ移行」タスクで実施する。
- Storage移行が完了したら `next.config.mjs` の `images.unsplash.com` remote pattern と fallback URL を削除する。

理由:

- 店舗写真の権利確認、primary管理、削除、差し替えを運営フローに乗せるため。
- OGPや検索結果で外部画像に依存すると、権利、表示安定性、LCP、ブランド品質の管理が難しくなる。
- ただし現時点で外部URLを即時削除すると、seed/fallback表示が壊れるため段階移行にする。

影響:

- 正式リリース用の初期店舗データには、権利確認済み画像の収集とStorage登録が必要。
- adminの店舗写真管理が、本番画像管理の主経路になる。

制約:

- 画像リサイズ、WebP/AVIF変換、サムネイル生成は未実装で、画像最適化タスクで扱う。
- 既存seedとfallback dataには、移行完了まで外部URLが残る。

## 2026-05-18: 口コミ非表示操作は未解決通報ステータスと連動する

決定事項:

- adminが通報一覧または口コミ一覧からレビューを非表示にした場合、そのレビューに紐づく `open` / `in_review` の通報を `resolved` に更新する。
- adminがレビューを再表示した場合、そのレビューに紐づく `open` / `in_review` の通報を `rejected` に更新する。
- 既に `resolved` / `rejected` になっている通報は、手動判断済みとして自動変更しない。

理由:

- 非表示操作と通報対応状況がずれると、対応済みの問題がadmin画面に未処理として残る。
- 再表示は「公開してよい」という運営判断なので、未解決通報は却下扱いに寄せる。
- 確定済みステータスを自動で上書きしないことで、手動運用の監査性を保つ。

影響:

- Hide/Restore 操作だけで基本的な通報処理が完結する。
- 個別通報ごとの細かい判断が必要な場合は、従来通りステータスを手動変更できる。

制約:

- 非表示理由、担当者、対応メモは未実装。
- 口コミの物理削除方針は別タスクで扱う。

## 2026-05-23: MVPの口コミ削除は非表示を削除相当として扱う

決定事項:

- MVPではadminによる `is_hidden` 切り替えを、公開面での口コミ削除相当の対応とする。
- 通報、削除依頼、権利侵害、プライバシー懸念への初動は、対象口コミを非表示にして公開ページ、評価平均、口コミ件数から除外する。
- 物理削除は正式リリース後の後続タスクとし、実装前に `review_photos` へ `storage_path` を追加してStorage上の画像も削除できるようにする。
- 物理削除を入れる場合は、削除理由、対応者、対応日時、関連通報/問い合わせとの紐づけを監査ログとして残す。

理由:

- 現行schemaの `review_photos` は画像URLのみでStorage pathを保持していないため、DBだけ物理削除するとStorageに孤児ファイルが残る。
- 非表示なら問題口コミを公開面から即時除外しつつ、通報・問い合わせ対応の証跡を保持できる。
- 店舗平均評価と `review_count` は既に非表示口コミを除外して再集計される。

影響:

- adminは当面、削除依頼への公開面対応として Hide を使う。
- 物理削除ボタンはまだadmin画面へ追加しない。

制約:

- ユーザー向けに「完全削除済み」とは表現せず、運営確認後に非表示または削除対応すると扱う。
- 個人情報や法的に即時削除が必要なケースが増えた場合は、物理削除と監査ログを優先実装する。

## 2026-05-23: 初期口コミは運営が捏造しない

決定事項:

- 初期データ投入では店舗情報、カテゴリ、都道府県、公式URL、住所、座標、営業時間、写真だけを整備し、運営が架空の口コミを作成しない。
- 公開環境の口コミは、実ユーザーの実体験に基づく投稿だけを表示する。
- 表示確認やseed用途でレビュー風データが必要な場合は、本番DBに投入せず、ローカル/プレビュー環境のテストデータとして扱う。
- 運営関係者が実体験に基づいて口コミを投稿する場合は、一般ユーザーと同じ投稿フローを使い、店舗関係者や利害関係者による評価操作は許可しない。

理由:

- 口コミサイトの信頼性は、レビューが実体験に基づくことに依存する。
- 初期表示を賑やかにするための捏造口コミは、利用規約の fabricated review 禁止方針と矛盾する。
- 初期SEOや検索体験は、口コミ数ではなく正確な店舗情報と権利上問題のない写真で補う。

影響:

- 正式リリース初期は口コミ数が少ない状態を許容する。
- 口コミ獲得は、店舗追加申請、共有導線、コミュニティ告知など実ユーザー投稿を促す施策で進める。

制約:

- seedやデモ表示にレビュー風データを使う場合は、本番環境と混同しない命名・環境分離が必要。
- 店舗オーナー、スタッフ、運営者、広告主による利害関係のある投稿の扱いは、正式なコミュニティガイドラインで追加整理する。

## 2026-05-23: 初期公開店舗は3重点都道府県で最低5件ずつ確保する

決定事項:

- 初期データ投入の重点都道府県は Tokyo、Kanagawa、Osaka とする。
- 正式リリース前の最低ラインは各重点都道府県5件以上、合計15件以上とする。
- 正式リリース目標は合計25件以上とし、内訳目標は Tokyo 10件、Kanagawa 8件、Osaka 7件とする。
- 各都道府県では Filipino Restaurant だけに偏らず、Filipino Grocery、Remittance Service、International Delivery Service も可能な範囲で混ぜる。

理由:

- MVP初期の検索体験では、対象地域を広げすぎるより重点地域で一定密度を作る方が見つけやすい。
- Tokyo、Kanagawa、Osaka は在日フィリピン人コミュニティとフィリピン関連店舗の初期探索対象として優先度が高い。
- 最低5件があると、都道府県ページと検索結果が空に近い印象になりにくい。
- 合計25件を目標にすると、トップ、検索、カテゴリページの初期表示に必要な厚みを作れる。

影響:

- seedの4店舗だけでは正式リリース不足で、追加調査とadmin登録が必要。
- 住所、座標、営業時間、電話、URL、写真権利の確認を店舗追加時の必須作業にする。

制約:

- 口コミ数はリリース判定に含めない。口コミは実ユーザー投稿で増やす。
- 店舗件数の水増し目的で未確認店舗や権利不明画像を登録しない。

## 2026-05-23: i18nはローカル辞書と非URLロケールで始める

決定事項:

- 初期の多言語対応は日本語・英語のUI文言切替に限定する。
- URLは当面 `/ja/...` や `/en/...` に分けず、既存URLを維持する。
- ユーザーの表示言語は cookie を主、必要なら `?lang=ja|en` を初回切替用に使う。
- 辞書は外部i18nサービスではなく、リポジトリ内のTypeScript定義で管理する。
- `Locale` 型は既存の `ja | en` を使い、辞書keyは機能単位で分ける。
- SEO用の多言語URL、`hreflang`、言語別canonicalは、日英ページをURLとして分離する段階まで導入しない。

理由:

- 既存ページURLとSEO導線を壊さずにUI切替を追加できる。
- MVPでは翻訳管理者や外部翻訳サービスを増やすより、コードレビュー可能なローカル辞書の方が運用が軽い。
- 日英URLを分けると、sitemap、canonical、OGP、検索流入、既存リンクの整理が必要になり、初期実装の範囲が広がる。

影響:

- 初期実装では同じURLで表示言語だけが変わる。
- Google検索向けの日英別インデックス最適化は後続課題になる。
- UI辞書化の対象は、ナビゲーション、フォーム、ボタン、エラー、静的説明文から始める。

制約:

- DB内の店舗説明やカテゴリ名は既に `nameJa` / `nameEn` を持つものを優先利用する。
- 口コミ本文、店舗名、住所、電話番号、URLは翻訳しない。
- URLロケール方式へ移行する場合は、redirect、sitemap、canonical、hreflangをまとめて再設計する。

## 2026-05-26: 地図UIはLeafletで実装する

決定事項:

- 検索結果と店舗詳細のアプリ内地図はLeafletを採用する。
- Next.js App Router では地図部分をclient componentとして切り出し、SSR対象から外す。
- 初期実装では既存の `lat` / `lng` を使い、検索結果はmarker一覧、店舗詳細は単一markerを表示する。
- OSM標準タイルを使う場合は、OpenStreetMap tile usage policyを守り、User-Agent/Referer、キャッシュ、過剰リクエスト抑制、attribution表示を前提にする。
- トラフィックが増える、またはOSM標準タイルの利用条件に合わなくなった場合は、有償/専用タイルプロバイダへ切り替える。

理由:

- 現在は外部OpenStreetMapリンクと擬似的な地図背景だけで、アプリ内で店舗位置を比較しにくい。
- Leafletは軽量なWeb地図ライブラリで、marker、popup、mobile操作、タイルレイヤーの基本機能が揃っている。
- Google Maps APIより初期費用とAPI key運用が軽く、MVPの店舗検索には十分。

影響:

- `leaflet` とReact連携用の実装が追加される。
- 地図コンポーネントはブラウザAPI依存になるため、dynamic importまたはclient component境界が必要。
- tile providerの選定とattribution表示が公開UIの一部になる。

制約:

- 大量アクセスや高頻度の検索更新ではOSM標準タイルへ負荷をかけない設計にする。
- 店舗データの座標精度が低い場合、地図UIの信頼性も下がるため、初期データ確認タスクと連動して進める。
- 参考: https://leafletjs.com/ / https://operations.osmfoundation.org/policies/tiles/

## 2026-05-23: 口コミ本文は原文を保持し、UI翻訳の対象外にする

決定事項:

- 多言語対応の初期スコープはUI文言、ナビゲーション、フォームラベル、エラーメッセージ、静的ページに限定する。
- 口コミ本文は投稿者が入力した原文をそのまま表示し、日本語/英語UI切替の対象にしない。
- 口コミ本文の自動翻訳を導入する場合は、原文を保持したうえで翻訳文を別フィールドまたは別表示として扱い、機械翻訳であることを明示する。
- 店舗名、住所、URL、電話番号などの事実データは翻訳せず、必要に応じて店舗説明やカテゴリ名など運営管理文言だけを日英管理する。

理由:

- 口コミ本文はユーザーの体験表現であり、翻訳によってニュアンスや責任範囲が変わる可能性がある。
- 日本語、英語、タガログ語、混在文など自由言語投稿を許容する方がコミュニティ実態に合う。
- MVPでは翻訳精度、モデレーション、法務対応、検索indexの複雑化を避ける。

影響:

- UI言語を切り替えても、既存口コミ本文は投稿時の言語のまま表示される。
- 将来のAI翻訳は、原文表示を壊さずに追加できる設計にする。

制約:

- 口コミ検索やモデレーションは原文ベースで行う。
- 翻訳済み口コミの保存、再翻訳、翻訳通報、翻訳品質管理は後続タスクとする。

## 2026-05-23: MVPの運営者情報は問い合わせフォームを正式窓口にする

決定事項:

- MVPの公開ページでは、運営主体を `KumustaHub operations team` と表記する。
- 削除依頼、修正依頼、プライバシー問い合わせ、モデレーション相談、提携相談の正式窓口は `/contact` とする。
- 個人の住所、電話番号、個人名は、正式な公開主体、連絡体制、法的表示要件が確定するまで公開しない。
- 収益化、広告販売、店舗向け有料掲載、法人化、特定商取引法など個別の表示義務が関係する機能を始める前に、公開範囲を再確認する。

理由:

- MVP段階では問い合わせフォームで運営対応の導線と監査記録を確保できている。
- 個人情報を過剰に公開すると、運営者側の安全性とプライバシーリスクが上がる。
- 将来の法人化や有料機能の有無で、公開すべき情報の範囲が変わる可能性がある。

影響:

- ユーザー向けの連絡先は `/contact` に集約する。
- 法務ページでは個別の住所や電話番号ではなく、問い合わせフォームを案内する。

制約:

- この判断は法的助言ではない。正式リリース、収益化、法人化の前に必要に応じて専門家確認を行う。
- 具体的な運営会社名、代表者名、所在地、メールアドレス、電話番号の公開は後続判断とする。

## 2026-05-23: 性能改善は正式リリース前後の後続タスクにする

決定事項:

- 現時点では性能改善を喫緊のP0として扱わず、原因調査と改善項目を `docs/TASKS.md` に残して後続対応にする。
- まずは費用を上げる前に、Vercel Observability と Supabase metrics で cold start、function duration、DB latency、Disk IO、connection pooler を確認する。
- コード側の優先改善は、公開ページの ISR 化、一覧用queryの軽量化、店舗詳細の重複DB取得削減、リージョン整合の順に進める。
- Supabase Free/Nano compute の制約が残る場合は、Pro/Micro 以上への移行を検討する。

理由:

- 2026-05-23 時点では体感の遅さはあるが、機能完成や運用安全性より優先度は低い。
- Vercel Hobby は現在 Standard CPU だが、serverless cold start は体感速度に影響しうる。
- Supabase Free は Nano compute で shared CPU、最大0.5GB memory のため、DB応答のばらつきやpauseの影響を受けやすい。
- 現行実装は公開ページでもリクエストごとにPrismaでDB取得しており、キャッシュ改善の余地が大きい。

影響:

- 当面は速度より機能・運用タスクを優先する。
- 正式リリース前に少なくとも主要ページのボトルネック確認は必要。

制約:

- 具体的な本番計測値はまだ取得していない。
- 実際の改善優先度は Vercel / Supabase の計測結果に基づいて見直す。

## 2026-05-17: プロジェクト管理ドキュメントは docs 配下の英名ファイルに統一

決定事項:

- プロジェクト管理ドキュメントは `docs/` 配下に配置する。
- 必須ファイルは `SPEC.md`, `TASKS.md`, `DECISIONS.md`, `CHANGELOG.md` とする。
- 補助ドキュメントは英名で追加する。

理由:

- `docs/RULES.md` のプロジェクト推進ルールに合わせる。
- Codexが作業前に参照すべきドキュメントを固定する。
- ファイル名の言語差による探索コストを下げる。

影響:

- 既存の日本語ファイル名は英名へ変更する。
- 今後の作業完了時は `TASKS.md` と `CHANGELOG.md` を更新する。

制約:

- 重要な判断はチャットだけに残さず `DECISIONS.md` へ記録する。
- 大きな仕様変更は `SPEC.md` も更新する。

## 2026-05-17: 店舗追加申請は admin 承認時に位置情報を補完する

決定事項:

- user の店舗追加申請は `store_requests` に保存する。
- 申請時は店舗名、住所、カテゴリ、都道府県、URL、補足だけを必須/任意入力として扱う。
- `stores` に必要な slug、緯度、経度、公開状態は admin 承認時に補完する。
- 却下時は `store_requests.status` と `rejection_reason` に記録する。

理由:

- 一般ユーザーに緯度経度入力を求めると申請ハードルが高い。
- 店舗公開前に運営が住所、重複、URL、カテゴリを確認する必要がある。
- `stores` の既存必須項目を崩さず、公開データの品質を保てる。

影響:

- 店舗申請から公開までは admin 作業が必須になる。
- 承認時の緯度経度入力ミスは地図表示に影響する。

制約:

- 現時点では申請写真のアップロードは未実装。
- 位置情報の自動ジオコーディングは未実装。

## 2026-05-17: 投稿abuse対策はDBイベントベースの user rate limit を先行する

決定事項:

- `rate_limit_events` に user id、action、quantity、created_at を記録する。
- server action の入口で直近ウィンドウ内の投稿量を集計し、上限超過時は保存やStorage uploadを行わない。
- 初期上限は以下とする。
  - 口コミ投稿: 5件 / 1時間
  - 口コミ写真アップロード: 12枚 / 1時間
  - 店舗追加申請: 3件 / 24時間
- Turnstile / reCAPTCHA は現時点では導入せず、連投やbotアクセスが実運用で確認されたら追加する。

理由:

- MVPではログイン必須投稿が中心のため、まず user単位の制限でDB/Storageの急増を抑える。
- CaptchaはUXと設定コストが増えるため、正式リリース前の最小対策としては後回しにする。
- DBイベント方式ならVercel serverless環境でも共有状態を持てる。

影響:

- 上限に達したユーザーは一定時間投稿できない。
- IP単位や匿名botの制御はまだ弱い。

制約:

- 厳密な同時実行制御ではないため、完全なスパム防止ではない。
- `rate_limit_events` は7日より古いイベントをserver action実行時に削除する。

## 2026-05-17: 店舗削除は物理削除ではなく archived 状態で扱う

決定事項:

- `stores.archived_at` を追加し、店舗の削除相当操作は archived 状態として扱う。
- archived 店舗は `is_published=false` にし、公開検索、店舗詳細、お気に入り一覧、投稿系操作から除外する。
- admin画面では archived 店舗も表示し、必要なら restore できる。

理由:

- 店舗に紐づく口コミ、通報、写真、お気に入りの参照を壊さない。
- 誤操作時に復旧できる。
- 法務・運用上、過去投稿の監査証跡を残しやすい。

影響:

- 公開側の店舗取得クエリでは `archived_at IS NULL` を必ず条件に含める。
- archive済み店舗は restore するまで publish できない。

制約:

- Storage内の写真本体はarchiveでは削除しない。
- 完全削除が必要な場合は、別途データ削除手順を設計する。

## 2026-05-18: Taxonomy削除は参照がない場合だけ許可する

決定事項:

- admin画面で `brands`, `categories`, `areas` を追加/編集/削除できるようにする。
- slugはtaxonomy種別ごとに一意とし、重複時は保存しない。
- 店舗、店舗追加申請、子カテゴリに参照されているtaxonomyは削除しない。
- `prefectures` は初期データ扱いとし、今回のCRUD対象外にする。

理由:

- 検索フィルタや店舗詳細URLにtaxonomy slugが使われるため、slug重複は公開導線を壊す。
- 参照中taxonomyを削除すると店舗登録、申請、検索フィルタの整合性が崩れる。
- 都道府県はMVPでは低頻度変更で、location追加時の親として選べれば十分。

影響:

- 都道府県単位location、カテゴリ、ブランドはコード変更なしで追加できる。
- 参照中taxonomyを消したい場合は、先に紐づく店舗や申請を移し替える必要がある。

制約:

- taxonomy自体のarchived状態は未実装。
- prefecture追加が必要になった場合は別途admin機能を追加する。

## 2026-05-18: 問い合わせはメール送信ではなくDB保存を先行する

決定事項:

- `/contact` から送信された問い合わせは `contacts` に保存する。
- 問い合わせ種別は `general`, `store_correction`, `deletion_request`, `moderation`, `partnership` とする。
- admin画面で問い合わせ一覧を表示し、`open / in_review / resolved / rejected` を更新できるようにする。
- メール送信はMVPでは導入せず、運用状況を見て必要になったら外部メールサービスを追加する。

理由:

- メール送信サービスの選定、送信ドメイン認証、到達率管理を後回しにできる。
- DB保存なら削除依頼、修正依頼、モデレーション相談の監査証跡を残せる。
- 既存admin運用と同じ画面で対応状況を管理できる。

影響:

- adminは定期的に問い合わせ一覧を確認する必要がある。
- ユーザーへの自動返信は現時点ではない。

制約:

- 返信は `mailto:` リンクなどを使った手動対応。
- 返信履歴や担当者メモは未実装。

## 2026-05-18: SEO base URL は環境変数で差し替え可能にする

決定事項:

- SEO用のbase URLは `NEXT_PUBLIC_SITE_URL` を優先し、未設定時は `https://kumusta-hub.vercel.app` を使う。
- `metadataBase`, canonical URL, sitemap, robots sitemap URL は同じbase URLから生成する。
- 店舗詳細には `LocalBusiness` または `Restaurant` のJSON-LDを出力し、口コミがある場合は `AggregateRating` を含める。
- OGP画像は当面、各店舗のprimary photoを使う。専用OGP画像制作は後続タスクに残す。

理由:

- 独自ドメイン確定前でも本番URLでSEO情報を破綻させない。
- 独自ドメイン移行時に環境変数だけでURLを切り替えられる。
- 店舗詳細ページは検索流入の中心になるため、構造化データを優先する。

影響:

- Vercel環境では `NEXT_PUBLIC_SITE_URL` を設定すればsitemap/robots/canonicalが差し替わる。
- OGP画像の品質は店舗写真の品質に依存する。

制約:

- 専用OGP画像は未実装。
- 外部URL画像の完全撤廃は初期データ/画像権利整理タスクで扱う。

## 2026-05-18: Location粒度は市区町村/駅単位ではなく都道府県単位にする

決定事項:

- 公開検索、店舗追加申請、admin店舗管理で選ぶlocationは都道府県単位にする。
- 既存DB互換性のため、DBテーブル名とPrisma modelは当面 `areas` / `Area` のまま維持する。
- アプリ層の型、関数、変数名は `Location` / `getLocations` / `locationId` に寄せる。
- 既存の細かいエリアレコードは都道府県レコードへ集約し、店舗と店舗追加申請の `area_id` を付け替える。
- URLは互換性を優先し、当面 `/areas/{slug}` を維持する。

理由:

- MVPの初期店舗数では Shinjuku / Ikebukuro などの細かい単位にすると検索結果が薄くなる。
- 都道府県単位の方が店舗追加時の運用判断が簡単で、ユーザーにも分かりやすい。
- 既存schemaを大きく壊さずに仕様変更できる。

影響:

- 旧 `ikebukuro`, `shinjuku-okubo`, `osaka-namba` などのエリアslugは使わなくなる。
- 検索フィルタ表示は `Tokyo`, `Kanagawa`, `Osaka` などの都道府県になる。
- 将来的に市区町村単位へ再拡張する場合は、別途location階層を設計する。

制約:

- DB層には `area` が残るため、Prisma query と SQL では `area_id` / `areas` を扱う。
- `/prefectures/{slug}` へのURL変更は未実施。

## 2026-05-18: アプリ層のlocation命名をAreaからLocationへ寄せる

決定事項:

- public UI は引き続き `Prefecture` と表示する。
- アプリ層の型、fallback data、DB取得関数、ページ変数、admin action名は `Location` に寄せる。
- DB schema、Prisma model、migration、既存URL `/areas/{slug}` は変更しない。
- 検索queryは新規フォームでは `location` を使い、旧 `area` queryも読み取れるようにする。

理由:

- `Area` は市区町村/駅単位に見えるため、都道府県仕様と認知がずれる。
- `Prefecture` に固定すると将来の市区町村・駅・地域タグ再拡張時に狭すぎる。
- DB/URL変更を避けることで、本番データとSEO導線への影響を抑えられる。

影響:

- 開発時は画面仕様に近い `Location` 名で読める。
- DB操作では `prisma.area` と `areaId` への変換が残る。

制約:

- `/areas/{slug}` は互換性優先で継続する。
- DB物理名の `areas` から `locations` への変更は正式リリース前の別判断とする。
